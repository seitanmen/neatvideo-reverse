## 3. PopcountGuarantee — 0x1561dec の popcount と var 面配列 (観測)

- 0x9aed78〜0x9aee74 は **popcount 型のカウンタ**: w8 = ubfx で保証語 `*(u32*)(image+0x1561dec) & 0x3fffff` の
  各ビット (bit0..21) を 22 回足し合わせ、0x9aee70 `sub w8, w8, #0x10`。
  つまり **PopcountGuarantee = popcount(保証語 & 0x3fffff) − 16**。
- ファイルの保証語 = 0x34f8d618 → &0x3fffff = 0x38d618 → popcount = 10 → **PopcountGuarantee = −6 (ファイル初期状態)**。
- PopcountGuarantee ≥ 16 のときだけ 0x9aed58〜0x9aed58 から FUN_009c80d4(alloc_ctx) が実行され、var 面の配列

  増設型アリケータ (既存の 0x50 バイトスロット配列が一杯なら FUN_009d7d5c で倍々に増設)。
  PopcountGuarantee < 16 なら 0x9aeecc `stp xzr, x2, [sp, #0x70]` で **配列ポインタは NULL**。
- したがって混合後処理の 0x9af230〜0x9af244 は、**PopcountGuarantee ≠ 0 のとき必ず image+0x1561d58 に 1 を書く**

## 5. 線カーネルのシフト x22 = [0x1561d58] と PopcountGuarantee の連鎖 (観測 + 推定)

- FUN_00990448 (線カーネル) は 0x9904c8 で **x22 = *(u64*)(image+0x1561d58) を読み**、0x9907a0 の
  `lsl x15, x15, x22` (浅い角度 (flag=1) のカーネルで「行数 = count << x22」) に使う。
  **u64 読み**なので、ファイル値 0x0000000096a78c49 (bit63 = 0、bits0-5 = 9) は「count を 2^9 倍」の
  意味で効く可能性がある (静的評価。この `lsl` が走るのは flag=1 の浅い角度のカーネルのみ。
  nv_lines.py の `self.lines` の count 欄に相当)。flag=0 (急な角度) の経路にこの lsl は無い。
- **訂正 (2026-10-21 深夜、最初の書き込みからの訂正)**: この値が何になるかは、**誰がいつ書くか**による。
  nv_lines.py の既存の注記 (行 103〜108) が正確だった:
  - `0x45114` を含む関数は RTTI **`14AbstractDrawer`** の仮想スロット 3 (vtable 0x13b5808、Qt 描画抽象クラス) で、
    0x45114 の `str x8, [x9, #0xd58]` は**座標変換の結果 4 つを out 引数に書く関数の末尾**にある
    (0x44f20〜0x44f3c で [sp+0x18/0x14/0x10/0xc] を x23/x22/x21/x20 へ、0x45114 はその後の別経路)。
    この関数は **描画のヒット判定/座標逆算** で、内容は「計算した 4 値のうち失敗時 0」を書くものとみられる
    (0x44f1c `fcmp s0, #0; b.ne 0x45138` → 非零なら 0x45138 の描画経路へ)。
  - つまり 0x1561d58 は「**直近の座標逆算の結果 x**」が入る作業欄で、**カーネル側はその値を shift 量として
    (u64 で) 流用して読んでいる**。ファイル値 0x96a78c49 は「まだ誰も書いていない初期ゴミ」。
  - 空間フィルタのチャンク末尾 (FUN_009ae918 0x9af230〜0x9af244) は PopcountGuarantee ≠ 0 のとき
    **[0x1561d58] = 1** を書く → 以後、浅い角度のカーネルは count << 1 になる。
    PopcountGuarantee = 0 (popcount(保証語&0x3fffff) = 16) なら書かないので、カーネルはそのときの
    直近値 (初期ゴミまたは別の書き手の値) を使い続ける。
- ハーネスの `nvh kernel` / `nvh curve` は FUN_009ae918 も 0x44dd4 も呼ばないため、
  **カーネルの照合・曲線の照合はすべてファイル初期値 (count << 9 相当) のまま行われた**。

  検証していない**。もっとも照合が全件一致した以上、ファイル初期値の下では等価 (count<<9 = count<<0 と
  なっている) か、あるいは lsl 経路は照合した角度では実行されていないかのどちらかである (推定)。

## 9. タスク 1〜3 の結果 (2026-10-22)

### 9.1 lsl は浅い角度だけ (観測)

### 9.4 影響の評価 (観測 + 试算)

## 11. トークン表の「書き手」の探索 (2026-10-22、ユーザー指示)

### 11.1 アドレス解決の仕組みが解けた (観測・検算済み)
トークンまわりの「ROOT スロット」(0x1488xxx、__data、dyld rebase 対象外) の生値は巨大な 64 ビット値に
見えたが、これは**設計された負のオフセット (2 の補数)** で、「ROOT + 巨大な正の即値」を 64 ビットで
計算するとキャリーが捨てられ、image+0x15xxxxx の欄が指される:
- *(0x1488CE8) = −0x18B18000、入口は +0x1A07EB80 → **image+0x1566B80** (AFT 入口の表ポインタ欄。
  REPORT §2.2 の記述と一致)
- *(0x1488CF0) = −0x15995978、+0x16EFF928 → **image+0x1569FB0** (AGENTS §6.5 の「語アドレスを
  image+0x1569fb0 に書く」欄 = watch-list。一致)
- *(0x14885C0) = +0x1232F3C、+0x00256F28 → image+0x1489E64 / *(0x14885D0) = −0x195664、
  +0x0161F9F8 → image+0x148A394 (ともに __data の語。FUN_0099afb4 の w19 = 0x1489E68 と同じブロック)
- FUN_00990f74 末尾 0x991f80: *(0x1487FD8) = −0x8B09B8、+0x1EA01E0 → image+0x15EF828 (__common)
つまり「表」の正体は **0x1561xxx〜0x1567xxx (__common、ゼロ初期化) の 8 バイト欄群**で、コード側は
「負オフセット定数スロット + 32 ビット即値」の 64 ビット加算で到達する。dyld の classic rebase は
__DATA_CONST のみ (全 2557 件が 0x13xxxxx、__DATA は 0 件) で、ROOT スロットは rebase も bind も
されない (dyldinfo -bind 0 行) — 負の値のままでも計算が正しく閉じる設計。

### 11.2 書き手の探索結果 (観測)
- 表ポインタ欄 (0x1566B80 / 0x1566BC0 / 0x1566B30 / 0x15636B8 / 0x1565418 / 0x15666C8 / 0x1569FB0 への
  書き込みを、(1) adrp 0x1561000 + add #0xf68 ベースの str (候補 8 件はすべて別アドレス着地)、
  (2) adrp 0x1488000 + str [x?, #0xc00〜0xd00] (0 件)、(3) mov/movk による直接アドレス生成
  (4 件はすべて別用途) — の 3 経路で全件検索したが、**1 件も存在しない**。
- 0x1561f68 をベースにするコードは 156 か所あるが、**すべて読み取り** (ldr/ldrb)。
- __mod_init_func (121 個) はどれも 0x148xxxx を触らない。
- したがって**この Mach-O の静的コードは表欄を書かない**。残る可能性は (a) ホスト側コンポーネント
  (ライセンス成立時に __common 欄へ書く)、(b) 自己書き換え / 動的生成コード (静的 disasm に現れない)。
- 「書かれない」場合の挙動は既知の観測どおり: *(image+0x1566B80) = 0 (NULL) → AFT 入口は cbz で
  代替パス → 本体が走らない (nvh info の条件値 4366324414)。**ハーネスで表 NULL なのは、書き手が
  バイナリ内に不在だから** (正常な動作で、欠けではない)。

### 11.3 AFT 入口条件値の検算 (補足)
- 定数語 0x1488496 = 0x822068fe (ファイル値、確認済み)。表 NULL 時の x + w = 0x0440D1FC、
  第 2 バイト 209・第 3 バイト 64 → 2·209 + 64 = 482 ≠ 0 (本体不成立)。
- `nvh info` の条件値 4366324414 = 0x10440D2BE = 2·w + 194 (2·w = 0x10440D1FC)。info 出力の合成式の
  内訳は未確認 (参考値)。

### 11.4 追跡の打ち切り理由
書き手がバイナリ外 (ホスト側) または自己書き換えである以上、静的解析ではこれ以上追えない。
実行時観測 (正規ホストのメモリダンプ) が必要で、これは本プロジェクトの手段の範囲外。
「表は正規ライセンス成立時にホストが埋める」という §2.3 の推定は、今回の構造解読 (欄が __common で
コード側は読み専用) と整合する。

## 12. 動的解析検証 (2026-10-24、ユーザーのライセンスで Resolve 版を登録して実施)

### 12.1 実施内容

- RS 版のバイナリをハーネスで dlopen + OFX 初期化 (setHost + Load) して `__common` の状態を観測
- 対照として OFX Demo 版 (無ライセンス) の `nvh probe` を実行

### 12.2 結果 (観測)

|---|---|---|
| トークン表ポインタ欄 (0x1566B80 等) | **全 7 欄 = NULL (0)** | `__common` に**非ゼロのヒープポインタが多数** |

### 12.3 確定したこと
1. **トークン表はライセンス成立時に dlopen (静的初期化) 中に書き込まれる** — OFX API 呼び出しの前でも
   `__common` に非ゼロデータが出現する (RS 版のプローブで確認)
2. **無ライセンスでは全トークン欄が NULL のまま** → 各保護ゲートは代替パスを通る → 保護対象の本体は実行されない
3. **RS 版はハーネス内でプラグインとして露出しない** (OfxGetNumberOfPlugins = 0) — ホストアプリ
   (Resolve) の.identity をチェックしているとみられる (推定)
4. **保護システムは実在し、ライセンス状態でアルゴリズムの実行パスが変わる** — v5 の再現では
   保護ゲートを通らないため、本体を実行しない経路と同じ数値になる (v5 は Demo の出力と一致していた
   のはこのため。ライセンス版では AFT 本体が走り、輝度別テーブルが変わり得る)

### 12.4 v5 への影響
- v5 は Demo 版の出力と比較してきた (PSNR 47.1 dB 等)。ライセンス版では AFT 本体が走り、
  輝度別テーブル (FUN_0099e6f4 の入力) が変わるため、σ マップが変わり得る
- ただし align_plan §4 の観測どおり「AutoFineTune なしのプロファイルでは輝度別テーブルが全て 1」
  であり、AFT が走ることでテーブルが 1 以外になる = σ マップが空間的に変化する
- **v5 で AFT を再現する**には、ライセンス版の AFT 出力 (テーブル) が必要。動的解析ではトークン表の
  内容までは読めていない (RS 版のアドレス配置が異なる + プロセスメモリの直接読み取りには権限が要る)
- 追跡はここで打ち切り (ユーザーのライセンスは Resolve 版で、OFX Demo 版の解析対象とは別製品のため)
