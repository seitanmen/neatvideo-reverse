## 2. フェーズと実行順

### Phase A: 実測による足場固め (agent-desktop による Resolve 自動化)
agent-desktop (導入済み、TMPDIR の修正が必要 — `/Users/seitan/.adt-tmp` を
`TMPDIR` にして呼ぶ。権限は Accessibility/画面収録済み) で Resolve を操作し、
本家の**実行時の数値**を観測する:
1. **.dnp のエクスポート観測**: 本家でプロファイルを作成・AutoFineTune 実行 →
   .dnp をエクスポート。バイト 74 (Noise Reduction Amount)、byte 222 (Temporal Radius)、
   既知の語に加えて **AutoFineTune が書き換えた輝度別係数の位置**を特定できれば、
   本家 AFT の実行時係数 (U4) を直接取得できる。
2. **GPU 有効/無効の A/B**: 本家の設定で GPU を切れる場合は両方で処理し、
   出力差 (U6) を測る。
3. **Manual Fine-Tune の R/G/B ビン編集の観測**: .dnp への書き込み位置と
   Quality (g) の変化を確認 (G1 の検証の強化)。
4. **素材ごとの処理設定の記録**: E9 の 4 素材 × σ3/σ6 について、
   本家が選んだ内部状態 (.dnp) を保存する。
- 成果物: `work/omo/wp_genuine_capture/` に .dnp と観測記録。
- 注意: ライセンスが有効な Resolve での作業。sudo で /Library/OFX/Plugins への
  インストールが要る箇所はユーザーの協力を得る。

### Phase B: U1/U2/U3 の静的解読 (統括が実施 — 保護区画を含む)
- U1: 0x991aac〜 の方向経路の逆アセンブル。組の選択条件、
  FUN_009ee7bc の適応経路の式、出力の合成を確定する。
  ハーネスで呼べる葉 (strip3・sigfuse 等) は照合済みなので、
  経路のオーケストレーションを解読して C++ (N1 の拡張) に実装 →
  `nvh` 相当の出力と本家ハーネスでビット一致を取る。
- U2: FUN_009ee7bc の入口から式を追う。
- U3: +0x17330 語 5+k の検証 (モデル面ブロックのレイアウト確定)。
- 合格: 本家ハーネス (`nvh`) で呼べる範囲の入力で、
  解読した経路の C++ 実装が本家とビット一致する。

### Phase C: AFT の実行時照合 (Phase A の .dnp と U4)
- Phase A で取得した本家 AFT の係数 (曲線 8 点 × 3 面) と
  nv_aft_v5 / aft_port の出力を比較する。一致すれば U4 は解消。
- 不一致なら、差のパターンから本家の係数の導出式を推定して修正する。

### Phase D: U5 (動き) の解読と実装
- パターン探索 0x98b9a4/0x98adbc の入口難読化 (BresenhamDrawer 系) の解読
  (保護区画。統括が実施)、平滑化 0x98c90c・レベル間伝播の照合、
  EstimateScaleMotion 本体。wp_motion の移植を C++ に取り込む。

### Phase E: v6 パイプラインの組み立てと最終比較
- 本家と同じ構成 (間引きラプラシアン + 白色化 + 方向組、MacroBlock 動き) を
  C++ で組み立て (N1 の部品 + Phase B/C/D の新規部分)。
- E9 の 4 素材 × σ3/σ6 で本家と比較し、PSNR の差をゼロに近づける。
- 旧 v5 は残す (参照・比較用)。

## 3. 保護区画の扱い

- トークン表の書き手はホスト側コンポーネント (静的解析の外) のため、
  AFT 本体はハーネスでは動かない。Phase A の .dnp 観測が代替手段。
- 保護区画を含む逆アセンブルは統括 (リード) が実施する
  (ユーザーからの一任済み)。C++ への実装は解読結果のアルゴリズムのみ
  (トークン表の構造自体は移植しない)。
